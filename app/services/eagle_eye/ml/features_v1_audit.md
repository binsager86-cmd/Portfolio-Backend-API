## Pipeline Architecture Clarification

**Two feature pipelines currently exist.** This is a known architectural issue surfaced by the verification.

| | `feature_builder.py` (v1) | `feature_builder_v2.py` (v2) |
|---|---|---|
| Used by | `data_pipeline.py` → feature store | `trainer.py` EagleEyeMLTrainer directly |
| Feature space | Large: context lookbacks, signal features, seasonality, regime, sector | Focused: 11 base indicators × 6 lag offsets + velocities |
| Negative sampling | Yes — random non-event rows sampled within ohlcv | Yes — random non-event rows with horizon check |
| Outcome labels | Computed via `_compute_trade_outcome` (future 20 bars) | Implicit in trainer binary label |
| Training pipeline | Not wired to trainer | Wired to `EagleEyeMLTrainer` |

**Resolution:** v1 feeds the feature store; v2 feeds the trainer directly. As of Phase 1, the trainer uses v2. The feature store (v1 output) is not yet consumed by the trainer. **This is a Phase 2 concern** — the trainer should be updated to consume the feature store (v1 pipeline). Until then, v2 is the active training pipeline and v1 is the data infrastructure layer.

## AST Scan — `feature_builder.py`

**Scanner:** `scan_source_for_leakage()` run on full source

**Finding:** 1 flag at line 319:

```
line 319: possible centered slice `iloc[i-w : i+w+N]` — verify this is not a future-look
```

**Analysis:** Line 319 is `future = ohlcv.iloc[accel_pos + 1: accel_pos + 21]`. This IS future data — but it is used exclusively to compute the **training target** (`tp1_hit_day`, `stop_hit_day`, `max_excursion_pct`). All three columns are listed in `NON_FEATURE_COLUMNS` and are excluded from the feature matrix by `get_feature_columns()`.

**Verdict: FALSE POSITIVE from the AST heuristic.** The forward slice is label construction, not a feature. The feature set does not contain any look-ahead values.

**Action:** Suppress this specific pattern in the AST scanner by moving label computation to a separate function with a clear name (e.g., `_compute_training_labels`). Flag for Phase 2 cleanup.

## Real Leakage Finding — Corporate Events (FIXED)

**Discovered in Check 4.**

**Original code (`corporate_events.py`, pre-fix):**
```python
future_divs = div_rows[
    div_rows["ex_date"].notna() & (div_rows["ex_date"] > t)
]
```

**Bug:** Filtered dividends by `ex_date > t` but did NOT gate on `announcement_date < t`. Result: a dividend announced on 2024-01-15 would show `days_until_next_dividend_ex_date = 22` on 2024-01-10 — data that was unknowable at that date.

**Impact:** Every training row where T < announcement_date but ex_date > T was contaminated. The model would learn to predict moves using information about events not yet publicly known.

**Fix applied:**
```python
future_divs = div_rows[
    (div_rows["announcement_date"] < t)   # announced before today
    & div_rows["ex_date"].notna()
    & (div_rows["ex_date"] > t)           # ex-date still in future
]
```
Same fix applied to `future_res` filter.

**Verification:** After fix, 2024-01-10 returns 365 (sentinel = no visible dividend), 2024-01-16 returns 16 (correct: 16 days to 2024-02-01 after announcement on 2024-01-15). ✅
